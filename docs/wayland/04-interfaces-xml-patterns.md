# Chapter 4: Interfaces, Requests, Events, and Protocol Patterns

> **Objectives.** By the end of this chapter you will be able to:

> - Read `wayland.xml`: interfaces, requests, events, args, enums, doc summaries.
> - Explain opcode numbering: from zero, in XML order, requests and events independently.
> - Describe atomic surface updates: pending state plus `commit`.
> - Handle object lifetimes on an async channel, including the destroy race.
> - Explain per-interface versioning, append-only growth, and unstable versus stable.

## 4.1 Requests versus events

Every Wayland message crosses a Unix-domain socket. Direction gives it its name:

- A **request** goes client to compositor: do something. `wl_surface.damage` means "repaint this rectangle".
- An **event** goes compositor to client: something happened. `wl_surface.enter` means "this surface is now visible on this `wl_output`", with the output passed as an object-id argument.

Wire format is identical both ways: object id, size-and-opcode word, then args (int, uint, fixed, string, object, new_id, array, fd). Decoding needs two lookups:

1. **Id to interface.** Each connection maps ids to types. Id 1 is always `wl_display`. Other ids are learned at creation: `wl_compositor.create_surface` assigns a new id both sides record as `wl_surface`.
2. **Opcode to signature.** The opcode indexes the message list for that interface *and direction*. Opcode 2 for `wl_surface` requests is unrelated to opcode 2 for `wl_surface` events.

Interface plus direction plus bound version selects the exact argument signature. Debug logs such as `WAYLAND_DEBUG=1` perform this same lookup to print symbolic names.

## 4.2 Reading `wayland.xml`

The core protocol is defined by `wayland.xml`, normally at `/usr/share/wayland/wayland.xml`. `wayland-scanner` turns it into headers and dispatch tables. Extension protocols reuse the same schema in their own files. Trimmed to two messages, `wl_surface` looks like this:

```xml
<interface name="wl_surface" version="6">
  <description summary="an onscreen surface">
    A surface manages a rectangular grid of pixels that the client
    provides and the compositor presents on screen.
  </description>
  <request name="damage">
    <description summary="mark part of the surface damaged">
      Notify the compositor that a rectangle of the surface content
      has changed and needs to be repainted on the next commit.
    </description>
    <arg name="x" type="int"/>
    <arg name="y" type="int"/>
    <arg name="width" type="int"/>
    <arg name="height" type="int"/>
  </request>
  <!-- attach, commit, set_opaque_region, ... omitted -->
  <event name="enter">
    <description summary="surface enters an output">
      Announce that the surface has become visible on the given output.
    </description>
    <arg name="output" type="object" interface="wl_output"/>
  </event>
</interface>
```

To read the real file, search for `interface name="wl_surface"` and note:

- `<interface name version>`: one object type; `version` is the newest dialect in this file.
- `<request>` / `<event>`: one message each. Names are symbolic; only the opcode travels.
- `<arg>`: one payload field, in order. Object args name their `interface`; nullable ones set `allow-null="true"`.
- `<enum>`: named integer constants: an int/uint alias documented by named constants; on the wire a 32-bit integer. Documentation and generated constants only.
- `<description summary>`: the normative comment. Read it before inferring meaning from arg names.

## 4.3 Opcodes come from document order

No name is sent. Each side agrees on numbers by reading the XML top to bottom:

- Requests numbered from zero in document order.
- Events numbered from zero in document order, on an independent counter.

Appending a request never renumbers older requests and never disturbs events. Simplified:

```text
requests (client -> server)    events (server -> client)
---------------------------    ---------------------------
destroy        opcode 0        enter          opcode 0
attach         opcode 1        leave          opcode 1
damage         opcode 2        (counter restarts; independent)
frame          opcode 3
... (document order continues)
commit         opcode 6
```

Verify with the `WL_SURFACE_*` defines generated by `wayland-scanner`; never hard-code opcodes. Concrete header words ground this: a `damage` request on object id 10 starts with `00180002` (length 24, opcode 2, then args 0/0/256/256), while an `enter` event starts with `000C0000` (length 12, opcode 0, then the output object id 5). Two consequences matter: sender and receiver must clamp to their negotiated interface version, since newer trailing messages may be unknown to the peer, and opcode tables are per-version views of the same XML. When versions differ, each side sends only what the bound version defines and must ignore or reject anything newer, which is why scanners emit version-gated symbols (forward pointer: details in Chapter 5).

## 4.4 Atomic updates: every frame perfect

Surface properties are coupled: attached buffer, damage, opaque region, input region, buffer transform, buffer scale. Applying them one by one would show torn states, such as a new buffer at the old scale.

So most `wl_surface` requests write **pending state**; `wl_surface.commit` promotes everything to **current state** at once. The slogan is "every frame perfect". Pending state covers buffer (`attach`), damage rectangles, opaque region (skip blending where opaque), input region (pointer and touch hit area), transform, and scale. A frame is `attach`, `damage`, `commit`, with nothing visible until the commit. Grouping also lets the compositor reason about each frame as one unit for scheduling, damage tracking, and presentation feedback. The same stage-then-publish shape recurs in subsurface sync and `xdg_surface` configure acknowledgements (forward pointers: covered in later chapters).

## 4.5 Lifetimes are asynchronous

Each direction preserves send order, but there is **ordering only per sender, none across directions**. A client request and a server event issued together can cross on the wire. Destruction is therefore a handshake:

1. One side sends the destructor, e.g. client sends `wl_keyboard.release`.
2. The peer processes it and drops its state.
3. The id is retired only once both sides agree.

In-flight strays are normal and must not crash the client:

```text
client:  handled key(a) ... release(keyboard) -------->
server:  ---- key(b) press ---> key(b) release ---> processes release
```

The `key(b)` events were valid when sent and arrive after the client destroyed its proxy. Correct code checks local proxy liveness before dispatching. The mirror direction matters too: had the client queued requests before destroying, it must send them in correct order so the object is no longer used after the agreed destroy. XML flags the end-of-life message with `type="destructor"` so generators tear down storage. Rule of thumb: creation agrees on a new id up front; destruction agrees the id is finished later. Design for the gap.

## 4.6 Versioning by appending

> **Misconception: "version means major.minor semver."** No. Each interface has its own monotonic integer (for example `wl_surface` 6, `wl_seat` 10 - check your `/usr/share/wayland/wayland.xml`; versions grow). Server and client negotiate one per bound object and clamp every message to it. Think per-interface dialect level, not product release.

Growth is **append-only**: new requests, events, and enum values go at the end. Nothing is removed or renumbered, so old opcodes keep working. The registry carries the negotiation: the server advertises each global with its maximum version, and the client binds at the minimum of what was offered and what its code understands. A version-6 client on a version-4 compositor simply never sends or expects version-5-plus messages.

One break is allowed: **unstable to stable** promotion. Experimental protocols ship as `zwp_*` or `zxdg_*` with an unstable-version warning. On stabilization they are renamed and cleaned up, and the unstable series freezes. Promotion is done so software can support both simultaneously for smoother transition. Treat every unstable protocol as breakable and gate it behind version checks. Many useful protocols (tablets, sync, color) lived years as unstable; unstable means the interface may move, not that the code is low quality.

## Recap

- Requests run client to server, events server to client; decode via id-to-interface then opcode-in-direction.
- `wayland.xml` is the spec: ordered requests, events, args, enums, summaries.
- Opcodes count from zero in XML order, independently per direction; appends preserve them.
- Surfaces batch buffer, damage, opaque/input regions, transform, and scale as pending state until `commit`.
- Destruction races: per-sender ordering only, handshake teardown, tolerate stray events, honor `type="destructor"`.
- Versions are per-interface integers; extend by appending, clamp to the peer; unstable may break once at stabilization.
